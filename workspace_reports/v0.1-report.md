# MLX-Tinker v0.1 — Comprehensive Project Report

## 1. Executive Summary

MLX-Tinker is a Tinker API-compatible LLM fine-tuning backend for Apple Silicon, built on MLX and mlx-lm. It implements the full Tinker API contract (as defined by Thinking Machines Lab and implemented by SkyRL-tx) but targets a single Mac with unified memory instead of CUDA GPU clusters.

**Current state:** Fully functional v0.1 with QLoRA fine-tuning, all API endpoints, 86+ passing tests (including real-model cookbook tests), and a profiled baseline on Qwen3.5-0.8B.

### Key design decisions vs SkyRL-tx

| SkyRL-tx (CUDA clusters) | MLX-Tinker (single Mac) |
|--------------------------|------------------------|
| Ray workers + NCCL sync | Single-process asyncio |
| Separate training/inference model copies | Same nn.Module for both (unified memory) |
| vLLM inference engine | mlx-lm generate_step |
| Postgres/SQLite + subprocess engine | In-process asyncio task + SQLite WAL |
| JAX/FSDP/Megatron backends | MLX nn.value_and_grad |

## 6. Profiling Baseline

### 6.1 Configuration
- **Model:** Qwen3.5-0.8B-MLX-4bit (124M params, 5.14% trainable with rank-16 QLoRA)
- **Dataset:** Dolly-15K (100 samples, max 256 tokens)
- **Hardware:** Apple Silicon Mac (unified memory)
- **Steps:** 50 training steps, single-sample SGD

### 6.2 Timing Breakdown

| Phase | Time | Notes |
|-------|------|-------|
| Model load | 19.8s | HuggingFace cache check + weight loading |
| QLoRA apply | 0.04s | Quantize + LoRA layers + freeze/unfreeze |
| Data load | 4.1s | Dolly-15K download + tokenization |
| JIT warmup | 0.76s | First forward+backward compiles Metal shaders |
| **Training (50 steps)** | **21.0s** | **Avg 0.42s/step, 201.6 tok/s** |

### 6.3 Per-Step Analysis

| Metric | Value |
|--------|-------|
| Average step | 0.42s |
| Median step | ~0.25s |
| Min step | 0.12s (20 tokens) |
| Max step | 1.22s (255 tokens) |
| Step time / token | ~5ms (linear in seq len) |

**Key observation:** Step time scales linearly with sequence length. The 10x variation (0.12s–1.22s) comes entirely from varying sequence lengths in Dolly-15K (20–255 tokens). No padding or batching is applied.

### 6.4 Memory Profile

| Phase | Active Memory | Peak Memory |
|-------|---------------|-------------|
| After model load | 0.42 GB | 0.42 GB |
| After QLoRA | 0.45 GB | 0.45 GB |
| During warmup | 0.50 GB | 4.13 GB |
| Steady-state training | 0.50 GB | 6.46 GB |

**Key observation:** Active memory is only 0.50 GB during training (the 4-bit model + LoRA weights), but peak memory reaches 6.46 GB — the ~6 GB gap is intermediate activations and gradients during backprop. These are freed immediately after each step (MLX lazy evaluation), explaining the constant 0.50 GB active memory.

### 6.5 cProfile Hotspots (training-time only)

| Rank | Function | Cumulative Time | Calls | % of Training |
|------|----------|-----------------|-------|---------------|
| 1 | `nn.value_and_grad` wrapper | 3.07s | 51 | 60% |
| 2 | `train_step` (total) | 3.21s | 51 | 63% |
| 3 | `mx.eval` | (included above) | — | — |

Training is fully **GPU-bound** — Python overhead is negligible. The `nn.value_and_grad` call submits Metal compute graphs; `mx.eval` synchronizes.

## 7. Optimization Opportunities

Based on profiling, ranked by expected impact:

### 7.1 High Impact

1. **`mx.compile` on train step** — Fuse the forward+backward+optimizer into a single compiled graph. Expected 1.5-2x speedup based on mlx-lm benchmarks.

2. **Sequence padding + micro-batching** — Currently processes one sample at a time with variable length. Padding to uniform length and batching 4-8 samples would amortize Metal kernel launch overhead and improve GPU utilization.

3. **Gradient accumulation across micro-batches** — Accumulate over N micro-batches before `optim_step` to simulate larger batch sizes without memory increase.

### 7.2 Medium Impact

4. **Gradient checkpointing** — Trade compute for memory on longer sequences. MLX supports `mx.checkpoint()` for recomputing activations during backward.

5. **Prompt caching for inference** — `LRUPromptCache` for repeated prefixes during RL sampling (same prompt, different completions).

6. **Async pipelining** — Use `mx.async_eval` to overlap data preparation with GPU compute.

### 7.3 Low Impact (for v0.1)

7. **Continuous batching for inference** — Currently sequential; batching sample requests would improve throughput 3-4x.

8. **Mixed precision** — Training already uses 4-bit quantized base; LoRA params could be kept in fp16 vs fp32.

# Unit tests (no model download, <5s)
uv run pytest tests/ -k "not stress and not cookbook"

# Cookbook tests (downloads Qwen3.5-0.8B, ~72s)

# Stress tests (requires torch + transformers)
uv sync --extra stress
uv run pytest tests/stress/ -m stress -v

## 11. Known Limitations

1. **No `mx.compile`** — The train step is not compiled, leaving ~50% performance on the table.
2. **Single-sample training** — No micro-batching; each step processes one sample at a time.
3. **Variable sequence lengths** — No padding; step time varies 10x based on input length.
4. **Deprecated MLX APIs** — Uses `mx.metal.get_active_memory()` which is deprecated in favor of `mx.get_active_memory()`.
5. **No learning rate scheduling** — Only constant LR via AdamW.
6. **Loss is noisy** — Single-sample SGD on diverse data produces expected high variance.
7. **Pre-quantized model for profiling** — The profile uses an already-quantized 4-bit model; quantizing from fp16 at runtime would add ~0.1s.
